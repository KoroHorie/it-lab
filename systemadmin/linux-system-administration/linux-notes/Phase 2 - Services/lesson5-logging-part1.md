# Phase 2 — Logging (Part 1: Introduction to journald)

## Why Do Linux Administrators Care About Logging?

Logs are one of the **first places** a Linux System Administrator investigates when something unexpected happens.

Logs usually answer the question:

> **"What happened?"**

They do **not** always tell you the root cause, but they almost always provide direction for your investigation.

Example production ticket:

```
Users report:

"The company's internal web application is unavailable."
```

Before making changes, the administrator wants evidence.

Instead of guessing:

- Is it a configuration issue?
- Is it a process issue?
- Is it a network issue?
- Is it a filesystem issue?

The administrator first asks:

> **"What do the logs say?"**

---

# The Troubleshooting Mindset

A professional Linux administrator does **not** immediately restart services or change configurations.

Instead, they investigate.

Typical workflow:

```text
Observe
    │
    ▼
Read Logs
    │
    ▼
Collect Evidence
    │
    ▼
Identify Possible Causes
    │
    ▼
Verify the Root Cause
    │
    ▼
Implement the Fix
    │
    ▼
Verify the Solution
```

Logs are the foundation of evidence-based troubleshooting.

---

# Why Was journald Created?

Before systemd existed, Linux primarily relied on traditional syslog daemons such as:

- syslog
- rsyslog

These daemons collected operating system logs.

When systemd was introduced, its developers asked a simple question:

> **"If systemd is already managing every service, why shouldn't it also collect every service's logs?"**

This idea led to the creation of:

```
systemd-journald
```

---

# What is journald?

`systemd-journald` is **systemd's logging service**.

Its responsibility is to collect log messages from:

- The Linux kernel
- systemd itself
- Services managed by systemd
- Various operating system components

Think of journald as the central log collector for a modern Linux system.

---

# Relationship Between systemd and journald

Throughout Phase 2, we learned that:

- systemd manages services.
- systemd manages units.
- systemd brings the system to its target state.

Now we add one more responsibility:

```
systemd manages services.

journald records what those services are doing.
```

This makes them tightly integrated.

---

# Conceptual Flow

```text
Linux Kernel
      │
      ▼
systemd (PID 1)
      │
      ├───────────────┐
      │               │
      ▼               ▼
nginx.service   NetworkManager.service
      │               │
      └───────┬───────┘
              ▼
      systemd-journald
              │
              ▼
       Journal Database
```

Every important component can send messages to journald.

---

# Production Example

Suppose an administrator executes:

```bash
systemctl restart nginx
```

If the restart fails:

The administrator expects journald to record messages such as:

```
nginx: configuration file syntax error

Permission denied

Failed to bind to port 80

No space left on device

Process exited with status code 1
```

These log entries provide direction for further investigation.

---

# What Logs Provide

Logs do **not** necessarily provide the exact root cause.

Instead, they provide:

- Error messages
- Warnings
- Service events
- Startup failures
- Shutdown events
- System messages

These clues allow administrators to narrow their investigation instead of guessing.

---

# Key Takeaways

## 1. Logging is an operational skill.

Unlike Boot Process, logging is something Linux administrators use constantly in production.

---

## 2. Logs answer the question:

> **"What happened?"**

before asking:

> **"Why did it happen?"**

---

## 3. journald was created because systemd already manages services.

If systemd starts, stops, and monitors services, it also makes sense for systemd to collect the logs generated by those services.

---

## 4. systemd and journald work together.

```
systemd
      │
      ▼
Manages Services

journald
      │
      ▼
Records Service Activity
```

---

## 5. Professional Linux administrators investigate before changing anything.

The first instinct is not:

```
Restart nginx.
```

The first instinct is:

```
Read the logs.
```

Evidence comes before action.
